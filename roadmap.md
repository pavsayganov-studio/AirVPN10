# Raketa — Roadmap

Список идей по трём осям: **современнее дизайн**, **надёжнее**,
**легче**. Каждый пункт проверен на совместимость с обязательными
требованиями из `README.md` (macOS 10.13, минимум CPU, System Proxy
архитектура) — здесь нет ничего, что требует их пересмотра.

Пункты внутри каждого раздела отсортированы от простого/безопасного к
более трудоёмкому. Ничего не помечено как «обязательно» — это меню, не
план спринта.

---

## Как читать этот документ

Каждый пункт — это:
- **Что** — суть идеи
- **Зачем** — какую проблему решает
- **Риск** — насколько безопасно это добавить, не сломав текущее
- **Проверка на 10.13** — если применимо, явное подтверждение что API
  доступен на минимальной версии

## 1. Дизайн — современнее, не теряя идентичность

### 1.1 Мягкие тени вместо только границ (низкий риск)
**Что:** добавить `layer.shadowOpacity` / `shadowRadius` карточкам
(Telegram-панель, главная кнопка) — не blur-эффект в реальном времени, а
статичная, один раз выставленная тень.
**Зачем:** сейчас разделение между слоями идёт только через цвет и
1pt-границу. Едва заметная тень (`shadowOpacity: 0.08`, `shadowRadius: 4`)
добавит глубину без анимации и без пересчёта на каждый кадр — CPU-cost
равен статичному border.
**Риск:** низкий. `CALayer.shadow*` — статичное свойство, не таймер.
**Проверка на 10.13:** `CALayer` shadow API доступен с самых ранних
версий `QuartzCore` — работает без ограничений.

### 1.2 Скруглённые dropdown и поля ввода (низкий риск)
**Что:** сейчас `NSPopUpButton` использует системный bezel «из коробки»
(прямоугольный с лёгким скруглением). Можно унифицировать со стилем полей
ввода — `cornerRadius` 6pt, заливка `rkSurface`, без системной рамки.
**Зачем:** визуальная согласованность — сейчас поле подписки скруглённое
кастомно, а dropdown серверов — системный. Разный радиус скругления
рядом читается как небрежность.
**Риск:** средний — кастомный `NSPopUpButton` без bezel требует ручной
отрисовки стрелочки-индикатора (иначе непонятно, что это выпадающий
список). Проверить читаемость перед принятием.

### 1.3 Более выразительная главная кнопка подключения (низкий риск)
**Что:** сейчас капсула с текстом «○ ВЫКЛ» / «● ВКЛ». Можно усилить
состояние «подключено» — например, тонкий градиент внутри капсулы
(`CAGradientLayer`, статичный, не анимированный) вместо плоской заливки.
**Зачем:** это единственный элемент, который заслуживает визуального
«якоря» — сейчас он выглядит так же плоско, как второстепенные кнопки.
**Риск:** низкий, если градиент статичный (`CAGradientLayer` без
анимации — задаётся один раз при смене состояния, не пересчитывается).
**Проверка на 10.13:** `CAGradientLayer` доступен с ранних версий
QuartzCore, ограничений нет.

### 1.4 Иконки состояния вместо только текста (средний риск)
**Что:** рядом со статусом («Подключено», «Ошибка») — маленький
Unicode-символ-индикатор (уже есть цветная точка, но можно усилить,
например ⚠ для предупреждений вместо только оранжевого цвета).
**Зачем:** дублирование сигнала цвет+форма помогает
пользователям с нарушением цветовосприятия — де-факто минимальный
accessibility-жест, который ничего не стоит по производительности.
**Риск:** низкий сам по себе, но требует аккуратной проверки рендеринга
символа на 10.13 (см. `design.md`, раздел 6, про безопасные Unicode-блоки).

### 1.5 Плавный (но статичный) переход при открытии Telegram-панели
**Что:** сейчас `toggleTG` дёргает `frame` мгновенно. Можно добавить
короткую (150–200ms) `NSAnimationContext` анимацию сдвига — уже
используется в старой версии кода (v0.7.1) и была признана избыточной,
но короткая версия дешевле, чем кажется: один проход анимации на клик
пользователя, не постоянный цикл.
**Зачем:** мгновенный скачок высоты попапа выглядит резко.
**Риск:** нарушает правило раздела 7 `design.md` («никаких
`NSAnimationContext` длительностью больше мгновенной подсветки»). **Это
единственный пункт в разделе, который требует явного решения — обновить
design.md, если принимается, а не тихое исключение.** Указан здесь
намеренно как пункт для обсуждения, а не готовая рекомендация.

## 2. Надёжность

### 2.1 Таймаут и повтор для загрузки подписки (низкий риск, высокая ценность)
**Что:** `downloadURL:` сейчас использует `NSURLSession` без явного
`timeoutInterval` — по умолчанию это 60 секунд, и при недоступном сервере
пользователь просто видит зависшую надпись «Загрузка...» минуту. Добавить
`request.timeoutInterval = 10.0` и на неудаче — понятное сообщение
(«Сервер не отвечает» вместо общего «Ошибка сети»).
**Зачем:** прямое улучшение UX при нестабильном соединении — частый
сценарий именно для целевой аудитории (обход блокировок).
**Риск:** минимальный, чисто аддитивное изменение с одной проверкой.

### 2.2 Валидация конфига перед записью на диск (низкий риск)
**Что:** сейчас `startVPN` пишет `config.json` и сразу пытается запустить
ядро. Если `outbound` содержит битые данные (например, пустой `server`
после неудачного парсинга vless-ссылки), sing-box просто не стартует, и
пользователь видит общее «Ядро не запустилось». Добавить лёгкую проверку
(непустой `server`, `server_port` в допустимом диапазоне) **до** записи
файла и запуска — с конкретным сообщением, что именно не так.
**Зачем:** конкретная диагностика вместо общей ошибки экономит время
пользователя на самостоятельный дебаг через «Логи».
**Риск:** низкий — чистая функция без побочных эффектов, добавляется
перед существующей логикой, не меняя её.

### 2.3 Права доступа на `config.json` (средний риск, стоит сделать)
**Что:** `config.json` содержит UUID пользователя и Reality-ключи в
открытом виде с дефолтными правами файла (обычно `644` — читаемо любым
локальным процессом того же пользователя). Установить `600` явно при
записи (`NSFileProtectionComplete` не актуален для macOS, но
`chmod` через `NSFileManager setAttributes:` — да).
**Зачем:** секреты сервера не должны быть читаемы кем попало на
многопользовательской машине.
**Риск:** низкий по коду, но стоит проверить, не блокирует ли это
доступ самого приложения при повторных запусках — тривиально
тестируется.

### 2.4 Явная проверка сетевого соединения перед стартом VPN (средний риск)
**Что:** если у пользователя вообще нет интернета (Wi-Fi отключён,
Ethernet не подключён), `startVPN` всё равно пытается запустить ядро,
которое просто не сможет достучаться до сервера — и пользователь видит
неинформативную ошибку. Быстрая проверка через `SCNetworkReachability`
(тот же фреймворк `SystemConfiguration`, уже используется в проекте для
`SCDynamicStoreCopyProxies`) перед запуском может сразу сказать «Нет
подключения к интернету» вместо «Ядро не запустилось».
**Зачем:** более точная диагностика самого частого случая «не работает».
**Риск:** средний — `SCNetworkReachability` синхронный вызов может
блокировать на доли секунды; нужно вызывать асинхронно или с явным
коротким таймаутом, чтобы не нарушить принцип «не блокировать UI».
**Проверка на 10.13:** API доступен с очень ранних версий macOS,
ограничений нет.

### 2.5 Автоматический перезапуск при однократном сбое ядра (высокий риск — обсудить отдельно)
**Что:** сейчас при падении ядра watchdog просто сбрасывает состояние и
просит пользователя нажать ВКЛ заново. Можно сделать одну автоматическую
попытку переподключения перед тем, как сдаться.
**Зачем:** меньше ручных действий при случайном разрыве соединения.
**Риск:** высокий — легко создать скрытый цикл переподключений, если
причина сбоя постоянная (например, неверный конфиг), что напрямую
противоречит CPU-приоритету проекта и урокам из истории (reconnect-storm
с Telegram, см. `handoff.md` §4.3). **Если делать — обязательно с
жёстким лимитом попыток (например, одна автоматическая, дальше только
вручную) и экспоненциальной паузой.** Помечено как пункт, требующий
отдельного обсуждения перед реализацией, не готовая к внедрению идея.

### 2.6 Проверка целостности sing-box перед запуском (низкий риск)
**Что:** если бинарник `sing-box` внутри `.app` повреждён или отсутствует
(редкий, но возможный случай при кастомной установке), сейчас это
приведёт к загадочной ошибке запуска. Быстрая проверка
`[fm fileExistsAtPath:bin]` перед вызовом AppleScript с понятным
сообщением («Файл ядра повреждён, переустановите Raketa»).
**Зачем:** конкретика вместо общей ошибки — тот же принцип, что 2.2.
**Риск:** минимальный.

## 3. Легковеснее

### 3.1 Ленивая загрузка Telegram-панели (низкий риск)
**Что:** сейчас `buildTGPanel:` вызывается в `loadView` при **каждом**
открытии попапа, даже если пользователь никогда не откроет саму панель.
Все её сабвью (лейблы, кнопки, разделители — порядка 15 объектов)
создаются заранее и просто держатся за пределами видимой области.
Можно строить панель лениво — только при первом нажатии на ✈.
**Зачем:** экономит ~15 объектных аллокаций и layout-проходов на каждое
открытие попапа, даже если Telegram-панель не нужна в этой сессии.
**Риск:** низкий — чистый рефакторинг lazy-init, не меняющий поведение,
только момент создания.

### 3.2 Освобождение неиспользуемых `NSTask`-объектов явно (низкий риск)
**Что:** в нескольких местах (`detectIface`, fallback в `coreAlive`)
создаются `NSTask` + `NSPipe`, но explicit `terminate`/`waitUntilExit`
дисциплина не всегда единообразна. Единая приватная обёртка
`runShellSync:` с гарантированной очисткой файловых дескрипторов пайпа
снизит риск накопления открытых хендлов при частых вызовах.
**Зачем:** long-running сессия с частыми ручными обновлениями подписки
теоретически может накапливать неосвобождённые дескрипторы — маловероятно,
но дёшево исправить один раз централизованно.
**Риск:** низкий, чисто внутренний рефакторинг без изменения внешнего
поведения.

### 3.3 Отложенная инициализация `cachedIface` (низкий риск)
**Что:** сейчас `detectIface` (форк `networksetup -listnetworkserviceorder`)
вызывается синхронно в `loadView` при **каждом** открытии попапа — даже
если пользователь просто взглянул на статус и закрыл окно, не трогая VPN.
Можно инициализировать `cachedIface` лениво — при первом реальном
`startVPN`/`stopVPN`, не при каждом открытии UI.
**Зачем:** это единственный оставшийся процесс-форк на пути открытия
попапа, который не обязателен, если пользователь не подключается.
Экономит один процесс-спавн на каждое случайное открытие иконки в
строке меню.
**Риск:** низкий — нужно только не забыть проверить `nil` перед
использованием в `startVPN`/`stopVPN`/`forceProxyOff`, что уже частично
сделано (`self.cachedIface ?: [self detectIface]` в `forceProxyOff`).

### 3.4 Сжатие бинарника sing-box сильнее (низкий риск, косвенный эффект)
**Что:** сборка уже использует `-ldflags="-s -w"` (убирает debug-символы).
Можно добавить `upx` сжатие бинарника в CI-пайплайне для уменьшения
размера `.zip`-релиза.
**Зачем:** быстрее скачивание для пользователя, не влияет на CPU в
рантайме (распаковка `.app` происходит один раз при установке).
**Риск:** низкий, но стоит проверить, что `upx`-сжатый бинарник
запускается без проблем именно на 10.13 (иногда старые системы
чувствительны к нестандартной структуре exec-секции после упаковки) —
тестировать перед принятием в постоянный пайплайн.

### 3.5 Убрать watchdog-таймер полностью, когда VPN выключен (уже сделано частично)
**Что:** текущий код уже останавливает `self.watchdog` в `stopVPN` —
хорошо. Стоит явно перепроверить, что `NSTimer` action держит `self`
слабой ссылкой (`__weak`) внутри блока, если такой появится в будущем
рефакторинге, чтобы избежать retain cycle. Сейчас используется
target-selector паттерн (`scheduledTimerWithTimeInterval:target:selector:`),
который безопасен по умолчанию — просто фиксируется здесь как правило на
будущее, если watchdog когда-то перепишут на блочный API.
**Зачем:** превентивная защита от утечки памяти при будущих правках.
**Риск:** нулевой — это правило, а не изменение кода сейчас.

## 4. Явно не рекомендуется (зафиксировано для будущих обсуждений)

Чтобы не переоткрывать эти вопросы каждый раз заново:

- **Не переходить на TUN/`utun`.** Разобрано и отклонено в `handoff.md`.
- **Не добавлять автоматическое фоновое обновление подписки по таймеру.**
  Прямо противоречит явному требованию «обновление только вручную»
  (`design.md` §7, `README.md` §2).
- **Не добавлять `NSVisualEffectView`/прозрачность фона.** Отклонено
  явным запросом пользователя ранее в проекте — «чистый, непрозрачный»
  зафиксировано как требование.
- **Не расширять поддержку на Apple Silicon/`arm64` без явного запроса** —
  см. `README.md` §1, universal binary не входит в текущий скоуп.

## Как использовать этот документ

Каждый пункт выше — кандидат, не решение. Перед реализацией любого
пункта:
1. Проверить, не противоречит ли он требованиям из `README.md` §2
   (CPU-приоритет) — большинство пунктов уже прошли эту проверку в
   формулировке «Риск», но финальное решение принимает человек, ведущий
   проект.
2. Реализовывать по одному пункту за раз, отдельным патч-скриптом с
   git-командами — по стандартному процессу проекта.
3. После реализации — обновить `handoff.md` (если меняется архитектура
   или добавляется новый паттерн) и/или `design.md` (если меняется
   визуальное правило), не оставлять новые решения незадокументированными.
